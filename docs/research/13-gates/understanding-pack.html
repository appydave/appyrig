Three gate systems and the thirteen gates

This page sums up what we learned from three systems that add code quality gates to an app. It also pins down what "the thirteen gates" means. The next phase checks AppyRig against them.

First, two words

A gate is a check that runs on every pull request and fails the build when the code breaks a rule. For example: no function longer than forty lines.

A ladder is a set of gates added one at a time, one pull request each, in a fixed order. The idea comes from Omer Gilad's spaghetti busters project. Don't ask the AI to write good code. Make the build fail when it doesn't.

02System one: the Spaghetti rig

This was a team of nine Claude sessions. There was a lead and an architect. Six desks each owned one tier of gates. A judge recommended keep or withdraw on every gate. David made the final call each time. A driver session outside the team planned the work and merged it.

It ran twice. The first run was on AppyRig, over two days. The second was on a game we built to be messy on purpose. That run took about a week and one hundred and thirty-six pull requests.

What worked

  • The gates really did change the messy game. Every unsafe type cast was removed. A nine-hundred-line class was split up. Test coverage of the game code rose to about sixty-five percent.
  • Having a separate judge caught results that had been gamed.
  • Each tier ended with a retro, and those retros became rules for the next rig.

What broke

  • The magic numbers gate ran away. It took thirty-three pull requests, until David stopped it. Half of its findings were in 3D model data, not in logic. The team invented new file formats when a library already existed.
  • The work was slow: a week, where Omer's pace was about a day per app.
  • The team stopped and waited at every tier boundary. The single judge became the bottleneck.
  • The structure got better, but the bugs stayed the same. A blind review scored the code about a third of a grade higher, at three times the lines.
  • Some rules were met by moving data out of the checker's sight. David sent the game back to the rig.

Lessons

  • If fixing a gate needs something new, you have stopped fixing that gate. Stop and ask the architect.
  • Data is not logic. Exempt it by name instead of converting it.
  • Look for a library first.
  • When every team member agrees, that is not the same as David agreeing.
  • Make the big decisions up front, with a price attached.

03System two: the AppyStack ladder

This was a smaller rig: a lead, an architect, one builder desk and a judge. This time the driver was a proper team member. It ran a trimmed ladder of ten gates on the AppyStack template. That took twenty-nine pull requests in about a day, including three releases.

What worked

  • Every merge followed the same rule: the judge said keep, and every check was green on that exact commit.
  • The number of tests went from one hundred and thirty to four hundred and thirty. A blind review moved the grade from C to C plus.
  • The architect caught a rule that would have broken new apps before anyone built it.

What broke

  • Version 0.5.0 shipped broken for new apps. No gate ever ran a freshly made app's own tests.
  • A fresh app failed its tests until one package was built by hand.
  • The blind review found twenty-four problems that the gates never touched. Four of them were serious, including Docker being unreachable.
  • The driver was connected to the rig the wrong way at first, so messages failed.

Lessons

  • An app that creates other apps has to create a fresh one and run it, from the very first tier.
  • The gates improved the things they measure. Everything that hurt a real user was found by running the app.
  • Test each proof by turning the rule down to a warning. The proof should fail.

04System three: the AppyTron ladder

This used the same team on the Electron template. It ran fourteen gates in twenty-four pull requests, over about a day. It added an audit after every few merges and a run of the real app at each tier end.

What worked

  • Merging and messaging worked the first time.
  • The judge planted fake bugs to test each gate, and that caught real holes.
  • Running the app early showed that a fresh app could not start at all. The Electron program was never downloaded. No gate could have seen that.
  • The driver blocked two rules that would have broken David's real apps.
  • David ruled it a working version, with three named exemptions.

What broke

  • The stall. After a reboot, the driver was reopened by hand and was not reconnected to its seat. The lead's messages bounced. About three and a half hours were lost before David asked, "are we finished?"
  • The test command slowed from about three seconds to forty-seven. Almost all of that was tests of the gates themselves, which add no app coverage.
  • One check passed locally but failed in the build, because the tool prints differently there.
  • About fifteen gigabytes of test apps were left on disk.

Lessons

  • Make the driver a real team member. Send decisions through the queue, not chat. After any restart, test messages in both directions.
  • Check every new rule against the real apps before it merges.
  • Keep the gate tests apart from the app tests.
  • Name every exemption in the open.

Four gates were only tried on the game: folder size, cohesion, coupling and stability. AppyStack put them off until a bigger app. The checks that found the bugs that hurt users are not on this list. They are the foundation checks and running the real app.

07Lessons that last beyond this job

  1. Gates are a fence, not a mop. They keep bad code out. They only clean up where there is a real mess, and they don't find behaviour bugs.
  2. Run the real app at the first tier. Make a fresh copy, install it, run it and upgrade it. Every break that hurt a user was found this way.
  3. Enforce correctness. Teach taste. Rules about type lies, size, dead code and boundaries earn their place. Rules about magic numbers and re-exports should be guidance for the architect instead.
  4. Check the fit before you fix. If a fix needs something new, it is a new problem. Ask the architect, look for a library, and give David a price.
  5. Name every exemption. A loosened rule doesn't count as working until David rules on it.
  6. Most rig failures were our setup, not OpenRig. Make the driver a real seat, and put decisions on the queue.
  7. Test new rules against the real apps, not just the template.
  8. Keep the scaffolding out of the numbers. Gate tests are not app tests.
